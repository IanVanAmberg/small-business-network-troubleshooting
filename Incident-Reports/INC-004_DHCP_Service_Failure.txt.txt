INC-004: DHCP SERVICE FAILURE

PROJECT: Northstar Office Solutions

ENVIRONMENT: Simulated Small-Business Network

INCIDENT ID: INC-004
CATEGORY: Network Connectivity
SUBCATEGORY: DHCP / Automatic IPv4 Configuration
PRIORITY: Medium (Simulated)
AFFECTED DEPARTMENT: New Employee Onboarding
AFFECTED DEVICE: PC-NewHire
FINAL STATUS: RESOLVED

--------------------------------------------------
1. INCIDENT DESCRIPTION
--------------------------------------------------

A simulated new employee reported that their workstation could not connect to the company network or access the internal employee portal.

The workstation was physically connected to the office switch but was unable to obtain the required network configuration automatically.

Existing employee workstations retained their previously assigned configurations and remained operational.

The objective was to investigate the failed DHCP address assignment, identify the affected service, restore automatic IPv4 configuration, and verify successful access to company resources.

The incident was successfully diagnosed and resolved through systematic troubleshooting without additional complications.

These baseline tests confirmed that the shared network infrastructure was operational before the incident.

Initial Network Status: OPERATIONAL

--------------------------------------------------
3. INCIDENT SIMULATION
--------------------------------------------------

The DHCP service on SRV-Infra was intentionally disabled.

The server's static IPv4 configuration, DNS service, and physical network connections were left unchanged.

A new employee workstation named PC-NewHire was added and connected to SW-Office using a Copper Straight-Through Ethernet cable.

The workstation was configured to request its IPv4 settings automatically through DHCP.

With the DHCP service disabled, the workstation failed to obtain a valid network configuration.

As a result, the new employee workstation could not communicate normally with the company network or access the internal employee portal.

Existing workstations remained operational because they retained their previously assigned DHCP configurations.

Simulation Result: SUCCESSFUL

--------------------------------------------------
4. DIAGNOSTIC PROCEDURE
--------------------------------------------------

STEP 1: REQUEST AUTOMATIC IP CONFIGURATION

Device:
PC-NewHire

Method:
Desktop > IP Configuration > DHCP

Purpose:
Determine whether the newly connected workstation could obtain network settings automatically.

Actual Result:
The workstation attempted to obtain its network configuration through DHCP.

The DHCP request failed because the centralized DHCP service was unavailable.

The workstation did not receive a valid Office Network configuration.

Result: FAILED AS EXPECTED


STEP 2: INSPECT WORKSTATION CONFIGURATION

Command:
ipconfig /all

Purpose:
Inspect the assigned IPv4 address, subnet mask, default gateway, and DNS server.

Actual Result:
The workstation did not possess the expected DHCP-assigned network configuration.

The missing valid Office Network settings prevented normal communication with company resources.

This finding was consistent with unsuccessful automatic address assignment.

Result: INVALID NETWORK CONFIGURATION IDENTIFIED


STEP 3: TEST LOCAL GATEWAY CONNECTIVITY

Command:
ping 192.168.10.1

Purpose:
Determine whether the workstation could communicate with its expected default gateway.

Actual Result:
The connectivity test failed.

The workstation was unable to communicate with the Office Network router interface because it had not obtained the required network configuration.

Result: FAILED AS EXPECTED


STEP 4: TEST INFRASTRUCTURE CONNECTIVITY

Command:
ping 192.168.10.10

Purpose:
Determine whether the workstation could communicate with the infrastructure server.

Actual Result:
The connectivity test failed.

Although the infrastructure server remained physically connected to the network, PC-NewHire lacked the valid IPv4 configuration required for normal communication.

Result: FAILED AS EXPECTED


STEP 5: VERIFY PHYSICAL CONNECTION

Device:
SW-Office

Interface:
FastEthernet0/4

Command:
show interfaces fastEthernet0/4

Purpose:
Determine whether the new employee workstation maintained an operational physical Ethernet connection.

Actual Result:
The switch interface displayed an operational status of up/up.

This confirmed that the workstation had an active physical connection to SW-Office.

The successful physical link verification helped eliminate a disconnected cable or inactive switch port as the cause of the reported connectivity problem.

Result: PASSED


STEP 6: COMPARE EXISTING WORKSTATION

Device:
PC-Operations

Commands:

ipconfig /all
ping 192.168.10.10
ping 10.0.0.10

Purpose:
Determine whether existing employee workstations retained their network configurations and connectivity.

Actual Result:
PC-Operations maintained its previously assigned IPv4 configuration.

The workstation successfully communicated with the infrastructure server and application server.

These results confirmed that the shared network infrastructure remained operational for devices with valid existing network configurations.

The comparison supported further investigation of automatic IP assignment rather than a widespread routing or physical connectivity failure.

Result: PASSED


STEP 7: INSPECT DHCP SERVICE

Device:
SRV-Infra

Location:
Services > DHCP

Purpose:
Determine whether the centralized DHCP service was available to respond to new client requests.

Actual Result:
The DHCP service was confirmed to be disabled.

This finding explained why PC-NewHire could not obtain the required network configuration.

The disabled DHCP service was identified as the direct cause of the new employee workstation's failed automatic IP assignment.

Result: ROOT CAUSE CONFIRMED

--------------------------------------------------
5. ROOT CAUSE ANALYSIS
--------------------------------------------------

Confirmed Root Cause:
DHCP service disabled on SRV-Infra.

Affected Service:
Dynamic Host Configuration Protocol

Affected Device:
PC-NewHire

DHCP Server:
192.168.10.10

Failure Type:
Centralized Network Service Outage

The DHCP service is responsible for automatically providing workstations with IPv4 addresses, subnet masks, default gateways, and DNS server information.

During the simulated incident, the DHCP service on SRV-Infra was intentionally disabled.

As a result, PC-NewHire could not obtain the valid network configuration required for normal communication with company resources.

Diagnostic testing confirmed that the workstation's physical Ethernet connection remained operational.

Existing workstations also retained connectivity, demonstrating that the router, switches, and application server remained functional.

The combination of failed DHCP assignment, missing valid workstation configuration, operational physical connectivity, and disabled DHCP service isolated the issue to DHCP service availability.

The incident also demonstrated that existing workstations may continue functioning during a DHCP outage while their previously assigned network configurations remain usable.

Root Cause Status: CONFIRMED

--------------------------------------------------
6. CORRECTIVE ACTION
--------------------------------------------------

The issue was resolved by restoring the centralized DHCP service on SRV-Infra.

Corrective Procedure:

A) Opened SRV-Infra and navigated to the DHCP service configuration.

B) Changed the DHCP service status from Off to On.

C) Verified that the existing DHCP address pool and network settings remained correctly configured.

D) Returned to PC-NewHire and opened its IP Configuration settings.

E) Triggered a new DHCP request by switching from Static to DHCP.

F) Confirmed that the workstation successfully received a valid IPv4 configuration.

G) Verified the assigned subnet mask, default gateway, and DNS server.

H) Tested local network connectivity and communication with the application server.

I) Verified DNS hostname resolution.

J) Confirmed successful access to the internal employee portal.

The corrective action successfully restored automatic IPv4 configuration for PC-NewHire.

No modifications to the router, switches, or application server were required.

Corrective Action Status: SUCCESSFUL

8. PREVENTIVE RECOMMENDATIONS
--------------------------------------------------

A) Monitor DHCP service availability to identify disruptions before they affect employee onboarding or address renewal.

B) Maintain accurate documentation of DHCP address pools, subnet masks, default gateways, and DNS server configurations.

C) Verify physical Ethernet connectivity before investigating DHCP service failures.

D) Inspect workstation IPv4 configurations when automatic address assignment fails.

E) Distinguish valid DHCP-assigned addresses from link-local or incomplete configurations.

F) Compare affected devices with existing functioning workstations to determine the scope of an incident.

G) Verify DHCP service status before making unnecessary changes to routers or switches.

H) Confirm that newly configured workstations receive unique IPv4 addresses to prevent address conflicts.

I) Perform complete post-resolution testing, including local connectivity, inter-subnet communication, DNS resolution, and application access.

J) Consider implementing DHCP redundancy and service monitoring in production environments where continued network availability is essential.

12. TECHNICAL OUTCOME AND LESSONS LEARNED
--------------------------------------------------

This incident demonstrated the importance of DHCP service availability in supporting automatic workstation network configuration and employee onboarding.

The simulated failure prevented a newly connected workstation from obtaining the network information required to communicate with company resources.

Systematic troubleshooting established that the workstation's physical Ethernet connection remained operational, while the DHCP service responsible for providing its IPv4 configuration was unavailable.

Comparing the affected workstation with existing devices helped distinguish a centralized DHCP service problem from a physical connectivity or routing failure.

The investigation also demonstrated that existing workstations may continue operating during a DHCP service outage because they retain previously assigned network configurations.

Restoring the DHCP service and renewing the workstation's network settings resolved the issue.

Successful validation of local connectivity, inter-subnet routing, DNS resolution, and HTTP access confirmed that the workstation was fully operational.

The exercise demonstrated a complete IT support troubleshooting workflow involving initial assessment, configuration inspection, fault isolation, root cause analysis, service restoration, and post-resolution verification.

This project stage provided practical experience with DHCP administration, workstation onboarding, TCP/IP diagnostics, Cisco switch interface inspection, network service troubleshooting, and professional incident documentation in a simulated small-business environment.
